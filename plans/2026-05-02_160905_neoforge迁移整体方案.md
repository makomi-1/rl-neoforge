# NeoForge 迁移整体方案

生成时间：2026-05-02 16:09:05

## 任务背景

目标是在 `D:\OpenProjects\RedstoneLink\rl-neoforge-1.21.1` 上，将 `D:\OpenProjects\RedstoneLink\rl-release-no-mixin` 的 Fabric 1.21.1 实现迁移到 NeoForge 21.1.219。

本次迁移遵循以下硬约束：

- 严格遵守 Fabric 版的设计与语义，不主动引入功能改造或行为变化。
- 迁移时优先保持代码结构、命名、模块边界与数据语义一致。
- 如存在平台差异，仅替换平台接入层，不重写业务层。
- 贴图、模型、语言文件、配方、loot table、blockstate 等资源如有缺口，可直接从 Fabric 侧复制。
- 迁移过程按阶段推进，每阶段以“该部分编译通过”为验收标准。
- 最终验收为客户端冒烟成功。

## 现状分析

### 代码体量与平台耦合分布

- Fabric 项目 `src/main/java + src/client/java` 共 371 个 Java 文件。
- 其中约 301 个文件可视为平台中立或仅依赖 Mojang/通用代码。
- 约 70 个文件直接依赖 Fabric API，主要集中在：
  - 入口与 datagen
  - 注册层
  - 网络注册与收发
  - 服务端/客户端事件
  - 客户端渲染、按键、HUD、世界交互
  - 配置路径解析

### 平台差异分层

1. 构建与元数据层
- Fabric：`fabric.mod.json`、Loom、Fabric datagen 入口。
- NeoForge：`neoforge.mods.toml`、ModDevGradle、`@Mod` 入口、事件总线驱动 datagen。

2. 注册层
- Fabric：`Registry.register` + `FabricBlockEntityTypeBuilder` + `FabricItemGroup`。
- NeoForge：`DeferredRegister`、`DeferredBlock/DeferredItem`、`DeferredRegister.create(BuiltInRegistries/Registries...)`、事件式创造标签填充。

3. 生命周期与事件层
- Fabric：`ModInitializer`、`ClientModInitializer`、`ServerTickEvents`、`ClientTickEvents`、`ServerLifecycleEvents`、`PlayerBlockBreakEvents`、`UseBlockCallback` 等。
- NeoForge：`@Mod` 构造注入 `IEventBus`、`NeoForge.EVENT_BUS`、`RegisterClientCommandsEvent`、`TickEvent`、`ServerStartedEvent/StoppingEvent`、`BlockEvent`、交互事件等。

4. 网络层
- Fabric：`PayloadTypeRegistry`、`ServerPlayNetworking`、`ClientPlayNetworking`。
- NeoForge：`RegisterPayloadHandlersEvent`、`PayloadRegistrar`、NeoForge payload handler 注册与上下文调度。

5. 客户端渲染与输入层
- Fabric：`BlockRenderLayerMap`、`HudElementRegistry`、`WorldRenderEvents`、`KeyBindingHelper`、客户端消息事件。
- NeoForge：客户端总线事件、`RegisterKeyMappingsEvent`、HUD/屏幕/渲染相关事件、`RenderLevelStageEvent` 或等价事件、菜单与 BER 注册事件。

6. 配置层
- Fabric：`FabricLoader.getInstance().getConfigDir()` + 自定义 `properties` 解析。
- NeoForge：配置文件路径可通过 `FMLPaths.CONFIGDIR` 获取；配置内容继续保留现有自定义解析与快照结构，不强制改造成 `ModConfigSpec`，除非 NeoForge 生命周期接入确有必要。

7. 数据生成层
- Fabric：`DataGeneratorEntrypoint` + `FabricRecipeProvider`。
- NeoForge：`GatherDataEvent` + NeoForge/Minecraft 官方 datagen provider 体系。

## 差异映射策略

### 总策略

采用“先平台骨架，后公共代码，最后平台接入层”的迁移方式：

1. 先让 NeoForge 工程具备稳定的构建、运行、资源装载与主入口。
2. 再迁移绝大多数平台中立类，使公共业务层尽快进入 NeoForge 编译图。
3. 对 Fabric 依赖点建立 NeoForge 适配层，逐类替换。
4. 每次只推进一个层级，避免整仓复制后出现大面积不可诊断错误。

### 各层实现原则

1. 业务类原则
- `com.makomi.data`、大多数 `block`、`block.entity`、`item`、`util`、`menu`、`advancement`、`command` 业务装配代码尽量原样迁移。
- 若仅因平台入口或注册方式不同导致编译失败，优先改平台接入点，不改业务语义。

2. 注册类原则
- 将 Fabric 风格静态注册表改为 NeoForge `DeferredRegister`。
- 对外暴露的符号命名保持一致，避免级联修改业务代码。
- 如有必要，引入 `Supplier`/`DeferredHolder`，但在使用侧尽量通过统一 helper 收敛差异。

3. 网络类原则
- 保持现有 payload 结构、字段语义、handler 分层与主线程切换逻辑。
- 替换的仅是注册 API 与上下文对象。

4. 客户端类原则
- 保持已有 GUI、世界外显、快捷键、HUD、网页桥接逻辑不变。
- 替换事件注册、包收发、渲染挂点、按键注册方式。

5. 配置类原则
- 保留 `properties` 文件格式、解析器、快照模型与访问门面。
- 仅调整配置目录解析与生命周期接入方式。

6. 资源类原则
- 资源优先整体复制。
- 若 NeoForge 对个别资源键路径要求不同，再做最小修正。

## 语义对齐说明

本次迁移严格保持 Fabric 设计语义：

- 节点语义继续保持 `triggerSource/core` 基线，与既有 `LinkNodeType.TRIGGER_SOURCE/CORE` 一一映射。
- 网络 payload、配置键、业务数据结构、命令树语义保持不变。
- 允许变动的仅是 NeoForge 平台接入方式，不改变业务规则。
- 若 NeoForge 平台对生命周期、注册顺序、渲染事件存在客观差异，将通过适配层吸收，不反向修改业务设计。

当前已知残余风险：

1. NeoForge 1.21.1 的客户端渲染挂点与 Fabric `WorldRenderEvents` 不完全等价，世界外显与 see-through 渲染可能需要单独收口。
2. 网络层自定义 payload 的注册口径与上下文对象需要逐包核对，属于中高风险迁移点。
3. 测试层若依赖 Fabric 测试基建，可能需要分阶段恢复，而不是一次性全部落地。
