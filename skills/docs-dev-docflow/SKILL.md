# Docs Dev 文档工作流

## 概览
基于用户聊天记录驱动 docs_dev 文档补充，按精简后的触发条件执行，并在必要时确认测试/审查与经验沉淀。

## 总体原则
- 当前目标工作区：`D:\OpenProjects\RedstoneLink\rl-neoforge-1.21.1`
- 当前目标分支：`migration/neoforge-1.21.1`（仓库初始化后生效；当前目录若未初始化 Git，则先跳过分支校验并报告）
- 仅在“代码/配置/资源改动”时要求详细方案确认
- 进入方案确认阶段时，回复末尾必须再用一句话简明扼要总结方案，便于用户快速复核。
- 版本号审查与升版提醒仅在用户提出提交要求后触发；未提出提交要求时不做版本号检查。
- 审查日志与测试记录不自动写入，仅提醒用户手动更新对应 xlsx。
- 仅当方案实现过程中出现明确阻塞点并已完成处置时，自动写入 `docs_dev/experiences/YYYY-MM-DD_HHmmss_任务名.md`，用于沉淀阻塞点与解决方法；不要把业务问题本身直接写成经验主题。
- 当实现过程阻塞较久时，先检索 `docs_dev/experiences/` 与 `docs_dev/经验总结.md`，再继续调试、调研或重试。
- 对反复复用或已稳定的“阻塞点 → 解决方法”经验，提醒用户定期沉淀到 `docs_dev/经验总结.md`，必要时继续固化到 `AGENTS.md` / `skills`。
- `README.md` 默认不纳入提交，除非用户明确要求提交该文件。
- 若任务涉及 spark profiler、spark health、bench 性能结果或热点分析，必须先读取 `docs/使用说明.md` 的 spark 相关章节，并以其中“Spark 报告直连分析”给出的机读方法作为默认分析路径。
- 仅依据用户聊天记录更新，不依赖计划文档反向补写。
- 仅更新头部明确标注“自动更新”的文档。
- 严格遵守文档自身格式与内容要求。
- 若本轮需要跑游戏内回归测试（含 dedicated server、bench functional、suite、物理世界场景），必须先构建当前工作区运行 jar，再同步服务器 jar；若 server/client 两端都要同步，统一复用同一次构建产物并按“先 server、后 client”顺序复制，未完成前不得把实跑结果当作当前代码验证结论。
- 若命中游戏内自动化测试修复、逐 tick 断言调整或波形异常排查，禁止按实测结果直接拟合实现、模板或结论；必须先复核实现设计与既有语义约束，再判断应修实现、修测试模板，还是记录观测口径偏差。
- docs_dev/references 为知识库，不与自动更新记录重复。
- docs_dev/plans 为方案文档区，仅在方案确认后写入。
- 目标文档缺失视为用户已手动迁移，只在汇报中说明，不创建新文件。
- 涉及贴图资源（`src/main/resources/assets/**/textures/**`）改动时，必须先发起“修改请求确认”并获得用户明确“确认”；未确认前仅允许只读分析。
- 若用户明确要求“只改渲染方式不改贴图”，必须将贴图文件列为禁止修改范围并严格执行。
- 分支校验目标固定为 `migration/neoforge-1.21.1`；每轮首次涉及 Git 操作前先确认当前目录已初始化 Git，再执行 `git branch --show-current`，不一致立即停止并报告。
- 任何回退动作（包括 `git revert/reset/checkout --/restore`、覆盖旧文件、删除后恢复）前，必须中断并向用户请求明确确认；未确认不得执行。
- 每次实现完成后，必须先执行一次全标签自动化测试回归：`.\gradlew.bat test testIntegration testClient testSlow testApiLegacy --no-daemon`。
- 语义术语基线：新增设计文档与实施说明统一使用 `triggerSource/core`，禁止新增 `button/source/target` 作为主术语。
- 语义兼容边界：旧术语仅可作为输入兼容说明；输出文案、字段命名、计划与结论必须统一为 `triggerSource/core`。
- 命中语义相关改动时，方案与结果必须附“语义对齐说明”（映射关系、方向校验、兼容策略与残余风险）。
- 每次实现完成后，必须自动生成审查文档 `docs_dev/reviews/YYYY-MM-DD_HHmmss_任务名.md`；文件名与方案文档命名规则一致，若目录不存在则创建。审查文档必须按“五段式审查（含并发冲突审查）”输出，并在每部分附 Markdown 绝对路径代码引用与具体行号。
- 结果汇报阶段仅简要总结改动、验证证据、语义对齐结论与残余风险，默认不附具体代码或文件引用；仅当用户明确要求时，再补充 Markdown 绝对路径代码引用，可附具体行号。
- PowerShell 读取中文文件前优先执行 `chcp 65001 > $null`，并在读取命令中显式指定 `-Encoding UTF8`。
- 文档写入优先使用 `apply_patch`，避免 PowerShell 重定向造成 BOM 或转码污染。
- 禁止使用 `>`、`Out-File`、`Set-Content -Encoding utf8` 对源码/文档执行整文件覆盖写入。
- 文件写入必须整块一次性写入，禁止拆段逐次写入。
- 构造待写入文档内容时禁止使用字符串 `+` 拼接多段文本，需使用完整文本块一次生成。
- 如必须脚本写入，统一使用 UTF-8（无 BOM）：`$enc = New-Object System.Text.UTF8Encoding($false); [System.IO.File]::WriteAllText($path, $text, $enc)`。

## 更新前检查清单（通用）
1. 目标文档头部是否明确“自动更新条件”。
2. 当前聊天记录是否满足触发时机。
3. 是否需要用户补充内容（审查/测试/经验/风险）。
4. 是否会与 references/plans 重复。
5. 计划写入方式是否满足“UTF-8（无 BOM）+ 非重定向覆盖写入”约束。
6. 如命中贴图资源改动，是否已完成“修改请求确认”（未确认不得写入贴图）。
7. 如命中游戏内自动化测试修复，是否已经明确设计依据，以及本次偏差属于实现缺陷、测试模板错误还是观测口径偏差。

## 索要内容规范（通用）
- 审查文档：实现完成后直接按“五段式审查（含并发冲突审查）”写入 `docs_dev/reviews/`，不等待用户补充模板结构。
- 审查日志：提交前确认对象与结论（通过/未通过），并提醒用户手动写入 `docs_dev/审查日志.xlsx`。
- 测试：提交前确认对象与结果（通过/未通过），并提醒用户手动写入 `docs_dev/测试记录.xlsx`。
- 经验库：仅在实现过程中出现明确阻塞点并完成处置后，直接提炼阻塞点、解决方法写入 `docs_dev/experiences/`；若已形成长期稳定规则，再提醒用户整理到 `docs_dev/经验总结.md` 或固化到 `AGENTS.md` / `skills`。
- 经验总结：当这些阻塞点处理经验已反复复用或需要抽象为长期规则时，再提醒用户沉淀到 `docs_dev/经验总结.md`。
- 风险：方案确认时若存在需保留风险，索要风险描述与规避方案。

## 文档级指引（含必填字段与模板示例）

### docs_dev/审查日志.xlsx
触发时机：提交前请求确认，且与测试记录对象一致；仅提醒用户手动写入，不自动更新该文件。

更新前检查清单：
- 用户是否明确“已审查”。
- 是否已给出审查结论（通过/未通过）。

必填字段清单：
- 审查对象
- 审查结果（通过/未通过）

向用户索要内容提示：
- 请确认审查对象与结论（通过/未通过）。

手动填写规则（提醒用户）：
- 文件：`docs_dev/审查日志.xlsx`
- 表头：`对象 | 通过 | 未通过`
- 规则：仅打勾/打叉，不记录时间与版本号。

### docs_dev/测试记录.xlsx
触发时机：提交前请求确认，且与审查对象一致；仅提醒用户手动写入，不自动更新该文件。

更新前检查清单：
- 是否完成测试。
- 是否已明确测试对象与结果。

必填字段清单：
- 测试对象
- 测试结果（通过/未通过）

向用户索要内容提示：
- 请确认测试对象与结果（通过/未通过）。

手动填写规则（提醒用户）：
- 文件：`docs_dev/测试记录.xlsx`
- 表头：`对象 | 通过 | 未通过`
- 规则：仅打勾/打叉，不记录时间与版本号。

### docs_dev/经验总结.md
触发时机：改动提交后询问是否需要，确认后写入。

更新前检查清单：
- 是否已完成审查。
- 是否有可复用经验要点。

必填字段清单：
- 解决要点（阻塞点 → 解决方法）

向用户索要内容提示：
- 审查已完成，是否沉淀经验？请给出经验要点。

输出模板：
```markdown
# 正文

[在正文最前插入]
- 解决要点：

2. 解决方法
```

### docs_dev/reviews/
触发时机：每次实现完成后，且进入结果汇报前。

更新前检查清单：
- 已完成本轮实现，能够明确关键入口、数据结构、调用链与风险点。
- 已拿到本轮关键改动的具体代码位置，能够附绝对路径行号引用。
- 审查文档文件名已按 `YYYY-MM-DD_HHmmss_任务名.md` 生成；若目录缺失则创建目录。
- 已完成并发冲突审查（共享状态、读改写覆盖、重入/线程边界），并形成风险等级与建议。

必填字段清单：
- 审查标题
- 1. 功能与语义、架构设计（关键方法和入口）
- 2. 关键数据结构和算法性能分析
- 3. 数据流或调用链
- 4. 安全、性能、兼容性、扩展性风险分析与建议
- 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）

输出要求：
- 五个章节必须全部存在，不得省略。
- 每个章节都必须附关键代码引用，格式使用 Markdown 绝对路径并带具体行号，例如 `[LinkSavedData.java](/d:/OpenProjects/RedstoneLink/rl-fabric-1.21.11/src/main/java/com/makomi/data/LinkSavedData.java#L52)`。
- 审查文档用于承载详细实现分析；任务汇报本身保持简短，不重复展开代码明细。

模板示例：
```markdown
# 审查标题

## 1. 功能与语义、架构设计（关键方法和入口）
- ...

## 2. 关键数据结构和算法性能分析
- ...

## 3. 数据流或调用链
- ...

## 4. 安全、性能、兼容性、扩展性风险分析与建议
- ...

## 5. 并发冲突审查（共享状态、读改写覆盖、重入/线程边界、风险等级与建议）
- ...
```

## 输出要求
- 所有新增记录必须可追溯且与聊天记录一致。
- 每次更新后列出修改过的文件清单与未完成项。
- 每次实现完成后必须先写 `docs_dev/reviews/YYYY-MM-DD_HHmmss_任务名.md` 审查文档，详细内容按“五段式审查（含并发冲突审查）”组织，并附具体代码引用行号。
- 结果汇报默认按“简要成果总结 → 验证证据 → 语义对齐结论 → 残余风险”组织；默认不附文件或代码引用，只有在用户明确要求时才补充 Markdown 绝对路径代码引用。
- 未收到明确提交指令前，不触发版本号审查/升版提醒，也不执行 `git commit`。
- 不自动改写 `docs_dev/审查日志.xlsx` 与 `docs_dev/测试记录.xlsx`，仅提醒用户手动写入。
- 提交阶段默认排除 `README.md`，仅在用户明确要求时才纳入。
- 若本轮命中语义相关改动，结果汇报必须单列“语义对齐结论”（通过项/风险项）。
- 若全标签自动化测试存在失败项，必须先汇报失败点与影响范围，不得按“已完成回归测试”输出结论。
- 每次写入后执行编码校验：首字节不得为 `EF BB BF`，并扫描是否出现替换字符 `�`。

## 上下文命中规则

### 事件 → 文档映射
- 完成方案实现 → `docs_dev/reviews/`
- 完成测试或明确未测试 → 提醒用户手动写入 `docs_dev/测试记录.xlsx`
- 提交前或用户已给出审查结论 → 提醒用户手动写入 `docs_dev/审查日志.xlsx`
- 方案实现过程中出现明确阻塞点并完成处置 → `docs_dev/experiences/`
- 审查完成且形成可复用经验 → `docs_dev/经验总结.md`
- 经验库内容反复复用或已稳定成规范 → 提醒用户沉淀到 `docs_dev/经验总结.md`、`AGENTS.md` 或 `skills`
- 方案确认且存在需保留风险/问题 → `docs_dev/保留问题.md`
- 新增/调整用户使用方式或命令 → `docs/使用说明.md`
- 方案确认后 → `docs_dev/plans/`

### 最小提问清单
- 标题/变更点名称
- 关键要点（按目标文档模板必填字段）
- 是否完成审查/测试（如适用）
- 是否需要保留风险/问题（如适用）

### 优先级说明
- 如与 AGENTS.md 冲突，以 AGENTS.md 为准。
- 仅更新头部明确标注“自动更新”的文档；目标文档缺失视为用户已手动迁移，只在汇报中说明，不创建新文件。
